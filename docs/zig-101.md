## 1. Orientation

`core/` is a Zig library with no external dependencies. It owns audio memory, the write path,
span reads, summary statistics, and WAV encoding. Python keeps audio capture and the Qt UI.

Four modules, plus a root:

| File | Job |
|---|---|
| `Ring.zig` | Single-producer, many-reader lock-free ring buffer. 913 lines, 16 tests. |
| `Summary.zig` | Pre-decimated stats ring: min/max/sum-of-squares/count per slot. 5 tests. |
| `wav.zig` | RIFF/WAVE writer. Header, quantization, streaming file write. 9 tests. |
| `abi.zig` | C ABI shim. Status codes, pointer-to-slice, nothing else. 13 tests. |
| `root.zig` | Library root. Re-exports the four, forces analysis. 1 test. |

44 `test` blocks total. Composition is one level deep: `Ring` *has a* `Summary`, and feeds it
inside `write`. `wav` knows nothing about `Ring`. `abi` knows all three and holds no logic.

The build graph is 26 lines (`core/build.zig`):

```zig
const mod = b.addModule("flashback_core", .{
    .root_source_file = b.path("src/root.zig"),
```
— `core/build.zig:7`

```zig
const lib = b.addLibrary(.{
    .name = "flashback_core",
    .root_module = mod,
    .linkage = .dynamic,
});
b.installArtifact(lib);

const tests = b.addTest(.{ .root_module = mod });
```
— `core/build.zig:15`

One module feeds two artifacts. `zig build` produces `zig-out/bin/flashback_core.dll` on
Windows (`zig-out/lib/` elsewhere); `zig build test` compiles the same module in test mode and
runs it. `linkage = .dynamic` is what makes it a shared library instead of a static archive.
Python loads that file with ctypes — see `flashback_sampler/core/native.py:43`.

Zig 0.16.0 is pinned in two places: `minimum_zig_version` in `core/build.zig.zon`, and the
`mlugg/setup-zig` version field in `.github/workflows/test.yml`. Zig is pre-1.0 and its
standard library moves; a version bump is a deliberate PR.

Shipped optimize mode is ReleaseSafe. Bounds checks stay on. Tests run in Debug.

## 2. Zig concepts, through this code

### 2.1 A file is a type

`Ring.zig:18`:

```zig
const Ring = @This();
```

Then the next lines are struct fields at file scope:

```zig
allocator: std.mem.Allocator,
frames: []f32, // storage_frames * channels, interleaved, one allocation, forever
capacity: u64, // in frames — the READABLE window; unchanged by the guard band below
```
— `Ring.zig:20`

The file *is* the struct. `@This()` names the enclosing scope, which at file scope is the file's
own type. `@import("Ring.zig")` returns that type, so `const Ring = @import("Ring.zig")` gives
you a type you can call `Ring.init(...)` on. `Summary.zig:10` does the same.

Coming from Python: there is no `class Ring:` line and no module-versus-class distinction. One
type per file, named by the filename. That is why `Ring.zig` and `Summary.zig` are capitalized
and `wav.zig` and `abi.zig` are not — the lowercase ones are namespaces of functions, not types.

### 2.2 Allocators are parameters

```zig
pub fn init(allocator: std.mem.Allocator, config: Config) !Ring {
```
— `Ring.zig:54`

There is no global heap. `std.mem.Allocator` is an interface value the caller supplies. Tests
pass `std.testing.allocator`; the ABI passes one shared instance (`abi.zig:17`). The struct
stores it so `deinit` can free with the same allocator that allocated.

The `!Ring` return type is an *error union*: either a `Ring` or an error. The error set is
inferred from the `try`s in the body.

### 2.3 `errdefer`, and the multi-`errdefer` init

```zig
const frames = try allocator.alloc(f32, storage_frames * config.channels);
errdefer allocator.free(frames); // runs only if a later `try` fails
@memset(frames, 0);
```
— `Ring.zig:68`

`defer` runs when the scope exits. `errdefer` runs only when the scope exits *with an error*.
Pair every fallible allocation with its own `errdefer` immediately after it, and a failure
halfway through construction unwinds exactly the allocations that succeeded. No `goto cleanup`
ladder, no leak.

`Summary.init` is the full version — five allocations, five `errdefer`s:

```zig
const min = try allocator.alloc(f32, n_slots * channels);
errdefer allocator.free(min);
const max = try allocator.alloc(f32, n_slots * channels);
errdefer allocator.free(max);
```
— `Summary.zig:28`

`Ring.init` keeps the pattern even where it is currently inert, and says so:

```zig
// No fallible operation follows before the return below, so this
// errdefer never actually fires today — kept as the same
// multi-errdefer pattern as `frames` above
errdefer summary.deinit();
```
— `Ring.zig:77`

`deinit` ends with a poison:

```zig
self.* = undefined; // poison: use-after-deinit becomes loud in Debug
```
— `Ring.zig:99`

In Debug, `undefined` is written as the byte pattern `0xaa`. Use-after-free reads garbage
loudly instead of reading plausible stale data quietly.

### 2.4 Error sets inside, status codes at the boundary

```zig
pub const ReadError = error{ Overwritten, OutOfRange };
```
— `Ring.zig:43`

An error set is a closed enum of error tags. `ReadError!void` means "void, or one of those
two". Callers must handle it — `try`, `catch`, or an exhaustive `switch`.

Error unions cannot cross a C ABI. So the shim converts:

```zig
export fn fb_ring_read(ring: *Ring, abs_start: u64, n_frames: usize, out: [*]f32) FbStatus {
    ring.read(abs_start, out[0 .. n_frames * ring.channels]) catch |err| return switch (err) {
        error.Overwritten => .overwritten,
        error.OutOfRange => .out_of_range,
    };
    return .ok;
}
```
— `abi.zig:237`

That `switch` is exhaustive over `ReadError`. Add a third error variant to `Ring.read` and this
file stops compiling. That is the point: the C boundary cannot silently forget a case.

`FbStatus` is `enum(c_int)` (`abi.zig:19`) so the numeric values are the C header's values.

### 2.5 Atomics and memory ordering

Three orderings appear, and each buys something specific.

**`.release` — the publish.** `Ring.write`:

```zig
self.summary.update(chunk, g, tw);
// The release-store PUBLISHES this chunk: everything written
// above becomes visible to any reader that acquire-loads a
// value >= tw + chunk_frames.
self.total_written.store(tw + chunk_frames, .release);
```
— `Ring.zig:187`

A release store guarantees that every memory write the thread performed *before* it is visible
to any thread that later acquire-loads that value. The audio data lands first, the counter
second, and no compiler or CPU may move the data writes after the counter store.

**`.acquire` — the observe.** `Ring.read`:

```zig
const t1 = self.total_written.load(.acquire);
```
— `Ring.zig:236`

An acquire load guarantees that everything the writer did before its matching release store is
visible to operations *after* this load. Pair one with the other and you get an ordered
handoff, without a lock.

**`.monotonic` — atomicity only, no ordering.**

```zig
const g = self.gain.load(.monotonic);
...
const tw = self.total_written.load(.monotonic);
```
— `Ring.zig:140`, `Ring.zig:162`

The writer reads its own counter. There is exactly one writer, so nobody else can change it and
no ordering is needed. Gain is a single `f32` with no dependent data, so a torn or stale read is
impossible and a one-block delay is harmless. `.monotonic` costs nothing on x86 and avoids a
barrier on ARM.

The code is honest about what this does *not* buy. From `Ring.zig:266`:

```
// (Formal-memory-model footnote, resolved: Zig 0.16 exposes no
// user-callable fence — `@fence` is an invalid builtin, ...
// An acquire load only orders operations AFTER it in
// program order — it does not order the copy ABOVE it relative
// to itself. On x86-64 ... TSO makes that a non-issue ...
// On a weakly-ordered target such as CI's aarch64 macOS runner,
// no such hardware guarantee exists, and the no-tear property
// for that platform rests on the stress test below, not on the
// memory model.)
```

Read that again when reviewing. The seqlock's second load is *supposed* to be ordered after the
copy, and Zig 0.16 gives no way to state that directly. On x86 the hardware does it. On ARM the
argument is empirical, not formal. That is an accepted, documented limit, not an oversight.

### 2.6 Exhaustive `switch` on enums

```zig
pub fn bytesPerSample(self: Subtype) u8 {
    return switch (self) {
        .float32 => 4,
        .pcm_24 => 3,
        .pcm_16 => 2,
    };
}
```
— `wav.zig:42`

No `else` branch. Add `pcm_32` to the enum and this switch is a compile error, as is
`formatTag` below it, as is the dispatch in `encodeSamples` (`wav.zig:103`). Three compile
errors that name the three places a new format needs a decision.

Coming from Python: this is the opposite of a dict lookup with a default. The absence of a
default is the feature. Use `else` only when you genuinely mean "and anything else".

The enum is explicitly backed by `u8` (`wav.zig:35`) because its values are wire values — the C
ABI passes 0/1/2. An unbacked enum's tag values are not guaranteed stable across compiler
versions.

### 2.7 Slices, many-item pointers, sentinel pointers

Zig distinguishes three pointer-ish things. Internally, everything is a slice:

```zig
pub fn write(self: *Ring, interleaved: []const f32) void {
```
— `Ring.zig:138`

`[]const f32` is a pointer *and* a length. Indexing is bounds-checked in Debug and ReleaseSafe.

C has no such type, so the boundary uses the other two:

```zig
export fn fb_ring_write(ring: *Ring, frames: [*]const f32, n_frames: usize) void {
    ring.write(frames[0 .. n_frames * ring.channels]);
}
```
— `abi.zig:190`

`[*]const f32` is a many-item pointer: an address with no length, exactly C's `const float*`.
The shim rebuilds a slice from pointer plus caller-supplied count. Note what that means — the
length contract now belongs to the caller, and Zig cannot check it. The ABI test says so
plainly at `abi.zig:63`.

For strings, the length lives in the data:

```zig
export fn fb_wav_write(path: [*:0]const u8, ...) FbStatus {
    ...
    wav.writeFile(std.mem.span(path), frames[0 .. n_frames * channels], rate, channels, st)
```
— `abi.zig:255`, `abi.zig:267`

`[*:0]const u8` is a sentinel-terminated pointer — C's `char*`. `std.mem.span` scans for the
zero and returns a proper slice. The sentinel is part of the type, so you cannot pass a
non-terminated pointer here by accident.

### 2.8 `export fn` and unmangled symbols

```zig
export fn fb_ring_create(rate: u32, channels: u16, seconds: f64) ?*Ring {
```
— `abi.zig:165`

`export fn` gives the function the C calling convention and an unmangled symbol name — the
DLL exports literally `fb_ring_create`. `pub fn` would not; it would only be visible to other
Zig code.

`?*Ring` is an optional pointer. In Zig, a plain `*Ring` can never be null; only `?*Ring` can.
On the C side both are just a pointer, and the header declares `FbRing *` — the nullability
information lives in the Zig type and in the documented contract, not in the C signature.

Note the asymmetry: `fb_ring_create` returns `?*Ring` and every other export takes `*Ring`. A C
caller that passes NULL to `fb_ring_destroy` has broken the contract, and nothing in the shim
checks it.

### 2.9 `comptime`

Two uses, both real.

An assert that runs at compile time:

```zig
comptime {
    // FLOAT32's memcpy path writes host-endian bits as file bytes.
    // Every supported target is little-endian; make that loud, not lucky.
    std.debug.assert(builtin.target.cpu.arch.endian() == .little);
}
```
— `wav.zig:9`

Cross-compile to a big-endian target and the build fails with a clear message, instead of
producing byte-swapped WAV files. The FLOAT32 path is a raw `@memcpy` of f32 bits
(`wav.zig:105`), so this assert is what makes that shortcut legitimate.

A force-reference that changes what gets emitted:

```zig
comptime {
    _ = abi;
}
```
— `root.zig:39`

Zig's semantic analysis is lazy. Declarations nobody references are never analyzed, and code
that is never analyzed emits no symbols. `_ = abi;` references the module, which forces its
declarations to be analyzed, which is what puts the `export fn` symbols into the DLL.

The spec commits to "no speculative comptime" (design doc, "Idiomatic commitments"). The code
holds to that: channels and sample rate stay runtime values.

### 2.10 `defer` ordering is LIFO, and it bit this codebase

Deferred statements run in reverse declaration order. That is not a detail — it caused a real
deadlock during construction, and the fix is commented in place:

```zig
// Defers run LIFO: stop must be signaled FIRST (declared LAST) so
// both joins below actually observe it and return. Declaring the
// signal before the joins (join-then-signal in source order, so
// signal-then-join in LIFO execution) deadlocked during development:
// flusher.join() ran before stop.store(true, ...) and waited forever
// on a thread whose loop condition could never go false.
defer writer.join();
defer flusher.join();
defer stop.store(true, .monotonic);
```
— `Ring.zig:813`

Read the three lines bottom-up to get execution order: signal stop, join flusher, join writer.
The ledger records the cost — `zig build test` hung for about three minutes locally and a CI
runner burned 68 minutes before a later push cancelled it. Three competing hypotheses were
raised and all three were wrong; the cause was defer order.

The rule: when defers depend on each other, read them bottom-up.

### 2.11 Testing: leak detection and reachability

Tests live in the file they test, in `test "name" { ... }` blocks. They compile only in a test
build.

```zig
var ring = try Ring.init(std.testing.allocator, .{ ... });
defer ring.deinit();
```
— `Ring.zig:289`

`std.testing.allocator` tracks every allocation. If a test ends with anything outstanding, the
test fails and prints the allocation's stack trace. Every test in this repo that constructs a
`Ring` or `Summary` is therefore also a leak test, for free. Forget the `defer ring.deinit()`
and the suite goes red.

Reachability is the sharper lesson. From `root.zig:12`:

```zig
// A `pub const` import alone is not enough: Zig's lazy Sema only analyzes
// declarations that are actually used, so an unreferenced `Ring` re-export
// would leave its `test` blocks (and any compile errors inside them)
// undiscovered — a build could report green having never looked at
// Ring.zig at all.
```

```zig
test {
    std.testing.refAllDecls(@This());
}
```
— `root.zig:28`

And the constraint that comes with it:

```zig
// IMPORTANT — `refAllDecls` is NOT recursive (`lib/std/testing.zig`'s
// implementation walks exactly one level of pub decls; 0.16 has no
// `refAllDeclsRecursive`).
```
— `root.zig:20`

**The operative rule: every new `core/src/*.zig` must get its own
`pub const X = @import("X.zig");` line in `root.zig`, or its tests never run and the suite
still reports success.** This is the single most important thing to know before adding a file
to this library.

One nuance the comment underplays, and which I reasoned rather than measured: the `test` block
is not compiled at all in the library build. So for `zig build` (the DLL), `comptime { _ = abi; }`
is not belt-and-braces — it is the only thing forcing `abi.zig`'s analysis, and therefore the
only thing emitting the exports. I did not verify this by deleting the block and inspecting the
DLL's export table.

## 3. The design decisions, and how they were reached

Sources: the code, and the execution ledger at
`.superpowers/sdd/2026-08-14-zig-core-phase1/progress.md`.

### 3.1 `total_written` is the single source of truth

**Decision.** One atomic counter of frames ever written. There is no stored write position and
no stored read position. The writer derives its slot as `total_written % storage_frames`
(`Ring.zig:163`). Readers address by absolute frame index and never look past `total_written`.

**What it buys.** Publishing is one store. `flush` is one store. There is no pair of counters
that can disagree.

**Rejected.** A claim-then-publish two-counter writer. The ledger's ruling R7 considered it as
the fix for a tearing bug and rejected it: it would have broken this invariant. The guard band
(below) was chosen instead precisely because it adds no atomic state.

**Consequence.** Everything stale past `total_written` is unreachable, so `flush` does not need
to zero memory for correctness. It zeroes anyway, because Python exposes the raw buffer as a
zero-copy view (`Ring.zig:102`).

### 3.2 The seqlock protocol

```zig
const t1 = self.total_written.load(.acquire);
if (abs_start + n > t1) return error.OutOfRange; // span not written yet
if (t1 - abs_start > self.capacity) return error.Overwritten; // already lapped
... copy ...
const t2 = self.total_written.load(.acquire);
if (t2 >= abs_start + n and t2 - abs_start <= self.capacity) return;
```
— `Ring.zig:236`–`283`, condensed

Copy first, validate after. Three attempts, then `error.Overwritten` (`Ring.zig:235`, `285`).

**What it guarantees.** A read that returns `ok` was not lapped during the copy. Readers never
block the writer.

**What it does not guarantee.** Progress. A reader losing every race gets an error, not data.
For a 900-second ring that is effectively never; the retry is insurance.

The `t2 >= abs_start + n` clause is checked first and is not redundant with the `t1` check.
`flush` can move `total_written` backwards to zero mid-read. Without that clause,
`t2 - abs_start` underflows an unsigned integer, which is illegal behavior and traps in Debug
*and* ReleaseSafe — a process abort inside a DAW. The full rationale is in place at
`Ring.zig:254`.

That bug was found by review, not by tests, and the ledger names it Critical 1. The test that
now covers it asserts only "never traps, and the result is `ok` or a documented `ReadError`"
(`Ring.zig:765`).

### 3.3 The guard band

This is the subtlest decision in the codebase. Read `Ring.zig:199`–`229` in full.

**The hole.** `write` copies a chunk into physical slots *before* it publishes. Those slots
previously held frames one lap back. A reader can be accepted by the validity check, copy from
slots the in-flight write has already overwritten, and then observe `t2 == t1` — zero apparent
writer progress — because nothing was published yet. It returns success with torn data.

Note the shape of the failure: not "rare", but *invisible*. The seqlock's own check cannot see
it, because the check is on a counter that has not moved.

**The fix.** Allocate more than the readable window.

```zig
const storage_frames: u64 = capacity + max_write_frames;
```
— `Ring.zig:67`

with

```zig
pub const max_write_frames: u64 = 4096;
```
— `Ring.zig:52`

`capacity` — the readable window — is unchanged, and both validity checks still test against
it. Only the physical size and the modulo arithmetic use `storage_frames`.

**The argument** (quoted from `Ring.zig:216`): with `P = storage_frames`, `C = capacity`,
`M = max_write_frames`, `P = C + M`, a writer publishing at `t` and about to write `b <= M`
frames will occupy the slots that held frames `[t-P, t+b-P)`. An accepted read satisfies
`abs_start >= t - C = t - P + M >= t + b - P`. So the reader's span and the writer's in-flight
block are disjoint by construction, not by probability.

**The rejected alternative, and why it was rejected.** The first ruling shrank the readable
window instead: `readable = capacity - max_write_frames`. Same disjointness, no extra memory.
It was reversed after checking the consumer. Python's `get_latest` clamps a request to
`min(tw, buffer_size)`, so asking for the full window asks for exactly `capacity` frames —
which the shrunken check rejects. "Give me the last 900 seconds" would return an empty array
after three retries. The ledger's own summary: *a fix that is locally correct can still be
wrong one layer up.*

**The cost.** 4096 frames of extra allocation. For a stereo f32 ring that is 32 KB, against a
345 MB ring — 0.009%. Five rings in the app, about 160 KB. Zero CPU cost.

**The consequence you must not forget.** The ring now has two sizes with different meanings,
and both are exported (`abi.zig:198`, `abi.zig:212`). Confusing them does not error; it
silently corrupts the waveform display. The header says so at `core/include/flashback_core.h:29`.

### 3.4 Chunked `write`, and why the limit became internal

The guard band's proof needs `b <= M` — every published block at most `max_write_frames`. The
first shape enforced that with an assert on the caller. That would have panicked on real use:
the existing Python suite writes multi-second blocks in one call.

So `write` chunks internally instead:

```zig
var remaining = interleaved;
while (remaining.len > 0) {
    const chunk_frames: u64 = @min(@as(u64, remaining.len / self.channels), max_write_frames);
```
— `Ring.zig:146`

Callers pass any size. Every individual release-store still advances `total_written` by at most
4096. A normal audio callback (64–2048 frames) takes exactly one iteration, so the hot path is
unchanged.

`max_write_frames` was demoted from a `Config` field to a file-level constant at the same time.
With chunking it is the ring's own publish granularity, not something a caller varies. That
also left `Config` byte-identical to its previous shape, so no downstream task had to change.

RT-safety survives: no lock, no allocation, no error path (`Ring.zig:130`).

### 3.5 Generation tags in `Summary`, and O(n_slots) poisoning

Each slot stores the absolute frame index of its first frame as a tag (`Summary.zig:24`).

```zig
const fresh = self.slot_abs[slot_idx] != slot_start_abs;
if (fresh) {
    self.slot_abs[slot_idx] = slot_start_abs;
    self.count[slot_idx] = 0;
```
— `Summary.zig:96`

Tag matches: accumulate. Tag differs: this slot belongs to an older lap, so overwrite. One
comparison replaces any clearing pass on wrap.

`flush` then has a problem. It resets `total_written` to 0, so absolute indices restart. A slot
still carrying its stale pre-flush tag can match a *new* write's recomputed tag — same number,
different epoch — and take the accumulate branch. Pre-flush and post-flush audio merge into one
slot's statistics.

The fix is one memset:

```zig
pub fn poison(self: *Summary) void {
    @memset(self.slot_abs, -1);
}
```
— `Summary.zig:67`

`-1` is not a valid absolute index, so no incoming span can match it. That is why `slot_abs` is
`[]i64` and not `[]u64` — the sentinel needs a value outside the domain.

The cost is O(n_slots), not O(frames). At 900 seconds with 4096-frame slots that is about
10,500 slots, versus 43.2 million frames. `flush` runs on a control thread, never the audio
thread.

The test that pins this is worth reading (`Ring.zig:866`): it writes `1,1,1,1`, flushes, writes
`3,3`, and asserts RMS 3.0. Without poisoning the answer is `sqrt(22/6) ≈ 1.915`. That number
is the whole point of the test.

### 3.6 32767 versus 32768

```zig
const v: i16 = @intFromFloat(std.math.clamp(@round(clamped * 32767.0), -32768.0, 32767.0));
```
— `wav.zig:120`

**Decision.** Scale by 32767, so `round(1.0 * scale)` stays in range without clamping. The
positive and negative rails are then symmetric at ±32767, and `-1.0` lands one LSB short of the
type's floor.

**Alternative.** libsndfile scales by 32768. That reaches the negative rail and clips the
positive one.

**Measured consequence.** For `x` in `[-1, 1]`, the two encoders' raw outputs differ by at most
`|x| + 1 <= 2` LSB — half an LSB of rounding from each encoder plus the scale gap. The proof
and its verification are at `tests/unit/test_native_smoke.py:97`: 40 random seeds plus a
200,001-point sweep of the domain, maximum integer gap exactly 2 in every case. The parity test
therefore uses a `2/32768` tolerance for PCM_16. A 1-LSB tolerance was genuinely impossible.

The bound holds *only* because the test data stays inside `[-1, 1]`. Above full scale this
encoder clamps while libsndfile's PCM path can wrap.

Note also `wav.zig:98`: NaN silently becomes full-scale positive, because `@min`/`@max` return
the non-NaN operand and `clamp`'s bounds are finite. NaN reads as loud, not as silence. This was
verified empirically on the pinned toolchain after an analytical prediction that it would trap
turned out to be wrong.

### 3.7 Serializing `fb_wav_write`

```zig
const wav_write_io = std.Io.Threaded.global_single_threaded.io();
var wav_write_mutex: std.Io.Mutex = .init;
```
— `abi.zig:54`

`wav.writeFile` reaches for `std.Io.Threaded.global_single_threaded`, the singleton std reserves
for "hardcode a synchronous Io" (`wav.zig:170`). Std documents that singleton as not supporting
concurrency. The reviewer traced the caveat to async/task-group paths that `writeFile` never
uses — but did not exhaustively trace every syscall wrapper.

**Decision.** Do not resolve the question; make it moot. Take a mutex for the call's duration.
`fb_wav_write` is an offline file write, never the audio thread, so a lock costs nothing that
matters.

**Rejected.** Documenting single-writer discipline at the ABI and leaving an open question on a
published C interface.

Two Zig 0.16 details worth noting here. There is no bare `std.Thread.Mutex` anymore — blocking
primitives moved under `std.Io`, which is why the mutex needs an `Io` value to block on.
`lockUncancelable` is used rather than `lock` because this `Io` has no cancelation source and an
`export fn` has no error path to plumb one through.

This is the only lock anywhere in the library. `Ring.write` is untouched.

### 3.8 Two sizes at the Python boundary

The guard band forced a decision on the host side. From `native.py:10`:

```
TWO SIZES, not one: fb_ring_capacity() is the READABLE window ...
fb_ring_storage_frames() is the PHYSICAL frame count backing
fb_ring_storage
```

Concretely (`native.py:161`):

- `buffer_size = fb_ring_capacity(...)` — every "how much audio can I get back" clamp.
- `self.buffer = np.ctypeslib.as_array(storage, shape=(storage_frames, channels))` — the
  zero-copy view's shape.
- `write_pos = total_written % self._storage_frames` — the physical position.

Using `capacity` for the view shape or the modulus does not raise; it silently reads the wrong
slots and corrupts the waveform display. Both sites were mutation-tested only after review
found neither was pinned (commit `4b6f2dc`).

## 4. Patterns and anti-patterns actually present

### Patterns worth keeping

- **The ABI shim holds no logic.** Every `export fn` in `abi.zig` is a type conversion plus a
  call. Validation guards are the one exception, and they exist because C callers are untrusted.
- **One source of truth for shared constants.** `Summary.max_bins` (`Summary.zig:77`) sizes the
  scratch arrays *and* backs the ABI's rejection test (`abi.zig:250`). It was a duplicated
  literal `4096` until review caught it.
- **Comments that carry rejected alternatives and their measurements.** `Ring.zig:424`–`513`
  records two failed test geometries with their numbers and an explicit "Do not re-run this
  experiment". That is expensive knowledge stored where it will be read.
- **Tests that name the mutation they survive.** `Ring.zig:382` explains why `abs_start=100`
  and not `abs_start=0`: at 0 the test passes whether or not the code under test exists.

### Accepted compromises, tracked as issues

**#20 — `flush` versus the writer** (`Ring.zig:102`). A writer that loaded `tw` before a flush
still publishes `tw + n` after it. `total_written` lands back near its pre-flush value while
every readable frame is zero. Up to a full capacity of silence, with no signal that a flush
happened. Cost: "Clear" during active capture can leave the buffer looking full of silence.
Accepted because fixing it means adding state to the RT publish path, which is an arc-level
design decision. Note the code comment corrected the spec here: the spec called it "at most one
audio block", which understates it.

**#21 — `Ring.init` does not validate its inputs.** `channels == 0` divides by zero in `write`;
a truncated-to-zero `seconds` degenerates the ring. Today this is masked because
`fb_ring_create` guards five clauses (`abi.zig:172`). That guard does not help a CLAP plugin or
a mobile shell constructing a `Ring` directly — which is the stated goal chain. Deliberately
left open after the ABI mitigation landed.

**#23 — `Summary.rmsBins` races `Summary.update`** (`Summary.zig:130`). The audio thread writes
slots while the UI thread reads them, with no atomics and no seqlock. The Python reference holds
a lock on both sides. Blast radius is genuinely small: fixed arrays, bounds-checked indices,
nothing derives a pointer or length from raced data, `bin_cnt == 0` is guarded, and a torn `ss`
yields NaN through the `sqrt` rather than a trap. Worst case is one wrong or NaN bin for one
frame at 30 Hz. Accepted because synchronization would touch the RT path. Worth knowing: the
parity harness can never catch this, because pytest is single-threaded.

**#26 — ctypes GIL tail latency.** Measured with a free-running writer and a competing reader,
three trials: Python's worst `write()` 0.58/0.52/0.52 ms; native 1.28/**2.98**/0.46 ms. Mean
throughput is about 6x better; the *tail* regresses. Mechanism: `ctypes.CDLL` releases and
re-acquires the GIL on every foreign call, so the worst case is bounded by
`sys.getswitchinterval()` (5 ms default), not by the copy. Phase 1 keeps capture in Python, so
this lands on the real audio callback thread. The spec always placed the jitter win in phase 2,
when capture moves to Zig and the write path stops crossing the GIL at all. This issue exists to
make sure phase 1 does not regress before then. No CI gate — the only test that touches writer
latency is marked `perf`, which CI excludes.

### Things I would flag that are not tracked

**A hidden two-channel ceiling in the engine.** `Summary.rmsBins` asserts:

```zig
std.debug.assert(chans <= 2);
```
— `Summary.zig:159`

`std.debug.assert` is live in ReleaseSafe, the shipped mode. `Ring.init` accepts any `u16`
channel count, and nothing in `Ring`'s or `Summary`'s public surface states the limit. Today
`fb_ring_create` rejects `channels > 2`, so the ABI path is safe. A direct Zig host — the CLAP
or mobile case — can build a 4-channel `Ring` that works until the first summary query, then
aborts. This is adjacent to #21 but is not what #21 describes.

**Unchecked narrowing casts on an ABI-reachable path.** `wav.zig:65`:

```zig
const block_align: u16 = @intCast(bps * channels);
const data_len: u32 = @intCast(n_frames * block_align);
```

Both abort the process in ReleaseSafe rather than returning `invalid_arg`. `block_align`
overflows above 8191 channels — unrealistic, and the ledger already deferred it as a minor.
`data_len` overflows above 4 GiB of payload, which is about 536 million stereo float32 frames.
Also unrealistic for this app (the 900-second ring is 43.2 million frames), but `fb_wav_write`
takes a `size_t n_frames` from any C caller, and RIFF genuinely cannot express more than 4 GiB.
The right shape is an `invalid_arg` return, not a panic. I found no issue covering `data_len`.

**96 KiB of stack scratch on a caller-supplied thread.** `Summary.zig:160`:

```zig
var bin_ss: [max_bins * 2]f64 = undefined; // max bins * max channels
var bin_cnt: [max_bins]u64 = undefined;
```

64 KiB plus 32 KiB, sized to the maximum regardless of the requested `n_bins`. The ledger's
pre-flight noted it and judged it within budget for a control thread, which is right for CPython
(8 MB default thread stacks). It is worth knowing before any future host calls this from a
thread with a small stack. Not tracked.

**A merged error case.** `Ring.read` returns `error.Overwritten` after three failed attempts
(`Ring.zig:285`) whether the cause was a genuine lap or a racing flush. `native.py:205` then
maps every error to an empty array. Callers cannot distinguish "your data is gone" from "try
again". This is small and probably right for phase 1, but it is a real loss of information.

**Deliberate dead code, kept and documented.** The outer clamps in `encodeSamples`
(`wav.zig:120`, `wav.zig:131`) have unreachable lower rails — the inner clamp already bounds the
input to ±1.0. Review confirmed the mutation does not redden any test. Kept as a defensive guard
at an ABI-adjacent boundary, with the rationale inline at each site. I mention it because it
will look like a bug on first read, and it is not.

## 5. Traps this codebase paid for

**Tests that pass without running.** Adding `pub const Ring = @import("Ring.zig");` to
`root.zig` did not make `Ring.zig`'s tests run. `zig build test` reported success while
executing zero of them. `std.testing.refAllDecls(@This())` (`root.zig:28`) is what actually
pulls them in, and it is not recursive. The rule that came out of it: after adding tests, check
that the test *count* rose. An exit code proves nothing.

**Mutation checks that do not redden.** The recurring defect of this build was a test that
looks like it pins something and does not. Three concrete cases: a poison assertion that called
`rmsBins(0, ...)`, which short-circuits on `n_samples == 0` before ever reading `slot_abs`
(`Ring.zig:863` now checks the field directly); a zero-length read test at `abs_start=0`, which
passes with the code under test deleted (`Ring.zig:382` now uses `abs_start=100`); and
`fb_ring_create`'s guard, which had *zero* coverage because every test passed valid arguments
(`abi.zig:118`–`150` now gives each of five clauses its own isolated test). One more, caught by
the implementer mid-write: proving round-half-away-from-zero with a `@floor` mutation fails,
because `@floor(-16383.5) = -16384` — the same answer. `@trunc` discriminates; the reasoning is
at `wav.zig:205`.

The general rule: a compound condition needs one mutation per clause, and the mutation must be
one that *should* change the answer.

**A stress test that could not detect what it existed to detect.** The seqlock stress test
(`Ring.zig:424`) reads at `tw - read_frames` with a 512-frame margin — nowhere near the boundary
the guard band protects. Removing the guard band entirely reddened nothing: 0/20 at one
geometry, 0/10 at another. The most important fix in the ring was pinned only by an assertion
about allocation size. The separate boundary test at `Ring.zig:623` fixed that: 20/20 clean
unmutated, 12/20 detecting guard-band removal, with a value signature ("one full lap ahead")
that confirms the failures are genuine. Getting there took decoupling two parameters that a
previous attempt had tied together — `block_frames = 3968` widens the writer's unpublished
window, `offset = 64` narrows the reader's tolerance. Coupling them made the effects cancel.

**Environment-shaped defects invisible on the dev machine.** Twice. First, `zig fmt --check`
failed on Windows CI only, because the repo had no `.gitattributes` and `core.autocrlf` rewrote
LF to CRLF on checkout. The committed bytes were LF the whole time; the fix is two lines in
`.gitattributes` pinning `*.zig` and `*.zon` to `eol=lf`. Second, three `wav.zig` tests
hardcoded a temp path that exists only on this workstation, and failed on all three CI runners.
The fix is `std.testing.tmpDir` (`wav.zig:243`), which builds a cwd-relative path under
`.zig-cache/tmp/` and cleans itself up. Both were green locally and red everywhere else.

**A useful meta-finding.** The ledger tallies three occasions where a confident analytical
prediction about runtime behavior was wrong and a measurement settled it: the `cap_frames`
detection arithmetic, the NaN-traps-in-`encodeSamples` claim, and skepticism about
`std.Io.Mutex` being real cross-thread exclusion. Zero occasions where analysis beat
measurement. For races and language semantics, run it.

## 6. Where to look next

Read in this order.

1. **`core/src/root.zig`** — 41 lines. Read it for the reachability rule before anything else.
   It determines whether the rest of the tests you read actually run.
2. **`core/src/Ring.zig:1`–`52`** — the module doc and the field list. This is where the two
   sizes are defined and distinguished. Nothing downstream makes sense without it.
3. **`core/src/Ring.zig:199`–`229`** — the guard-band note above `read`. The hardest argument in
   the codebase, written out in full.
4. **`core/src/Ring.zig:138`–`195`** — `write`. Read it for the RT-safety invariant: no lock, no
   allocation, no error path, chunked publishing.
5. **`core/src/Summary.zig:83`–`118`** — `update`. The generation-tag trick in 35 lines.
6. **`core/src/abi.zig`** — the whole file. Read it for the boundary rules: status codes,
   many-item pointers, sentinel pointers, and the five-clause input guard.
7. **`core/src/wav.zig:35`–`140`** — the `Subtype` enum through `encodeSamples`. Read it for
   exhaustive switches and the quantization contract.
8. **`flashback_sampler/core/native.py:1`–`20` and `:144`–`186`** — the host side of the
   two-sizes split.

Then the tests. `Ring.zig:623` (guard band) and `Ring.zig:866` (poisoning) are the two that pin
the least obvious behavior, and both carry their reasoning in comments.
